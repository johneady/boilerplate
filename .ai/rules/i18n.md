# Translations

## Two key conventions, split by where the string lives
Both are live at once and that is deliberate, not drift:

- **Blade and Livewire copy uses the English source text as the key**, resolved from `lang/en.json`: `{{ __('Get started') }}`. Prose reads as prose in the template, diffs stay reviewable, and a missing entry renders the English rather than a raw key.
- **Filament labels, notifications and enum copy use dotted keys** in `lang/en/{users,settings}.php`: `->label(__('users.fields.email'))`. These are short, structured and repeated (the same "Role" label appears on a form field, a column and a filter), so one key feeding several call sites is worth the indirection.

Adding a user-facing string means adding it to whichever file matches where it lives. Do not "unify" the two — converting the ~240 JSON entries to dotted keys was considered and rejected: a mistyped dotted key renders the key itself to the user and no test fails, which is a bad trade for copy that is already readable in place.

## Framework-free classes must not call __()
`App\Auth\Role` and `App\Auth\Permission` return plain English from `label()`, `description()` and `color()`, and must keep doing so. They are covered by `tests/Unit/RoleTest.php`, and tests/Pest.php binds `TestCase` to `Feature` only -- a unit test has no container, so `__()` there dies with "Target class [translator] does not exist." Wrapping those enums cost a full-suite failure once; translate role copy at the point of display (the Filament resource) instead.

The same applies to anything else reached from tests/Unit: check for a unit test before adding `__()` to a class outside the HTTP/Filament layers.

## Never concatenate a translated string
`'Mailer: '.$this->mailerLabel()` is untranslatable by construction -- word order is not the same in every language, and a translator never sees the whole sentence. Use a placeholder: `__('settings.mailer.button', ['mailer' => ...])`. Two of these existed on the settings page and both are now placeholders.

## __() returns string|array once replacements are passed
With a replacements array the translator's return type widens to `string|array`, so assigning it straight into a closure declaring `?string` fails PHPStan at level 8. The array arm is unreachable for a string key. Cast it in a named method with a comment (see `ManageSettings::mailerTooltip()`) rather than casting inline at each call site or widening the closure's return type.

## The error pages deliberately stay on JSON keys
`resources/views/errors/**` must render with the database down and the route cache broken (.ai/rules/errors.md). English-as-key means that even a completely missing translation file renders correct English rather than `errors.404.heading`. Do not move these to dotted keys.

## Server report labels are translated at the point of display
`App\Settings\ServerInformation` returns plain English array keys ('Operating system', 'Memory limit'); the Blade template passes each through `__($label)`. Those strings are in `lang/en.json` like any other copy. Keep new rows' labels in that file -- a label added to the class without a JSON entry still renders, so nothing fails loudly.

## A test guards every dotted key
`tests/Feature/TranslationsTest.php` asserts every dotted key referenced in `app/` resolves to a string that is not the key itself, which is the failure this convention is otherwise blind to. It also asserts no `__()` call concatenates. Run it after adding strings.
